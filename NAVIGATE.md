## ⚡ Competitive Programming

Competitive Programming (CP) is the practice of solving algorithmic and computational problems under constraints such as time, memory, and input size.

It helps develop the ability to:

- Break complex problems into smaller parts
- Identify patterns and approaches
- Choose suitable data structures and algorithms
- Analyze time and space complexity
- Handle edge cases
- Write efficient and correct solutions

### 🧠 CP vs DSA vs Coding Interviews

| Area | Main Focus |
|---|---|
| **DSA** | Learning data structures and algorithms |
| **Competitive Programming** | Applying algorithms to solve problems efficiently under constraints |
| **Coding Interviews** | Solving problems while explaining your reasoning and approach |

DSA provides the foundation, while Competitive Programming provides extensive problem-solving practice.

---

### 🧱 Core Topics

A practical progression:

**Programming Fundamentals → Complexity → Arrays & Strings → Sorting & Searching → Hashing → Two Pointers & Sliding Window → Stack & Queue → Linked Lists → Recursion & Backtracking → Trees & BST → Heap → Graphs → Greedy → Dynamic Programming → Number Theory → Combinatorics → Advanced Algorithms & Data Structures**

You do not need to master everything before starting problems. Learn a concept, practice it, identify your gaps, and move forward.

---

### 🔍 Problem-Solving Patterns

Important patterns that appear repeatedly:

- Brute Force → Optimization
- Sorting + Greedy
- Hashing
- Two Pointers
- Sliding Window
- Prefix Sum
- Difference Array
- Binary Search
- Recursion
- Backtracking
- Divide and Conquer
- Greedy Algorithms
- Dynamic Programming
- Graph Traversal
- Shortest Path
- Disjoint Set Union
- Bit Manipulation
- Number Theory

The goal is not to memorize solutions. The goal is to recognize which technique can be applied to a new problem.

---

### 🛠️ Problem-Solving Workflow

1. Understand the problem
2. Identify inputs, outputs and constraints
3. Think of a brute-force solution
4. Analyze its time and space complexity
5. Find the bottleneck
6. Look for a better algorithm or data structure
7. Implement the solution
8. Test edge cases
9. Submit
10. Review what you learned

If you cannot solve a problem, try:

**Think → Experiment → Get a Hint → Study the Solution → Reimplement → Solve a Similar Problem**

---

### 🏁 Contests

Contests provide experience that normal practice does not completely reproduce.

They help you practice:

- Solving under time pressure
- Choosing which problems to attempt
- Managing failed approaches
- Debugging quickly
- Reading constraints carefully
- Thinking independently

After a contest:

**Contest → Review Unsolved Problems → Read Editorials → Understand the Missing Idea → Reimplement → Upsolve**

The learning after a contest is an important part of the process.

---

### 🔄 How to Practice Effectively

Avoid solving random problems endlessly.

Instead:

**Learn a Concept → Solve Easy Problems → Solve Medium Problems → Attempt Unfamiliar Problems → Review Mistakes → Revisit the Concept → Move to the Next Topic**

Keep a simple record of:

- Problem name
- Topic
- Difficulty
- What you learned
- Why your approach failed
- Important pattern or technique

---

### ⚠️ Common Mistakes

- Memorizing solutions without understanding them
- Ignoring constraints
- Starting advanced topics too early
- Solving only familiar problems
- Never reviewing failed submissions
- Avoiding contests because of low ratings
- Focusing only on the number of problems solved
- Copying solutions without reimplementing them

The objective is **better problem solving**, not simply a bigger solved-problem count.

## 🐙 Git & GitHub

Git and GitHub are essential tools for modern software development.

**Git** is a distributed version control system used to track changes in code and manage different versions of a project.

**GitHub** is a platform built around Git that helps developers store repositories, collaborate, review code, manage projects, and contribute to open source.

They are related, but they are not the same thing.

---

### 🧠 Git vs GitHub

| Git | GitHub |
|---|---|
| Version control system | Online development platform |
| Runs locally on your computer | Primarily accessed online |
| Tracks changes in files | Hosts Git repositories |
| Uses commits and branches | Adds collaboration and project-management features |
| Can work without GitHub | Built around Git repositories |

**Git → manages your code history**

**GitHub → helps you store, share and collaborate on that code**

---

### 🧱 Basic Git Workflow

A common workflow:

**Create / Clone Repository → Make Changes → `git status` → `git add` → `git commit` → `git push`**

For an existing remote repository:

**`git pull` → Make Changes → `git add` → `git commit` → `git push`**

---

### 💻 Essential Git Commands

| Command | Purpose |
|---|---|
| `git init` | Initialize a Git repository |
| `git clone <url>` | Copy a remote repository locally |
| `git status` | Check the current repository state |
| `git add <file>` | Stage a file |
| `git add .` | Stage multiple changes |
| `git commit -m "message"` | Save staged changes as a commit |
| `git log` | View commit history |
| `git diff` | View changes |
| `git branch` | View branches |
| `git switch <branch>` | Switch branches |
| `git switch -c <name>` | Create and switch to a branch |
| `git merge <branch>` | Merge a branch |
| `git pull` | Fetch and integrate remote changes |
| `git push` | Upload local commits |
| `git remote -v` | View remote repository URLs |

You don't need to memorize every command at once. Learn them through actual projects.

---

### 📦 Understanding Commits

A commit is a recorded point in your project's history.

Good commit messages describe what changed:

- `Add login page`
- `Fix navigation bug`
- `Update README`
- `Add sorting algorithms`
- `Improve responsive layout`

Avoid vague messages such as:

- `changes`
- `update`
- `final`
- `done`

A useful pattern is:

**Change → Stage → Commit → Push**

---

### 🌿 Branches

Branches allow you to work on changes separately from the main development line.

Example:

**`main`**

**`main` → `feature/login`**

**`main` → `feature/dashboard`**

**`main` → `fix/navbar`**

A typical workflow:

**Create Branch → Make Changes → Commit → Push Branch → Open Pull Request → Review → Merge**

Branches are especially useful when multiple people are working on the same project.

---

### 🔀 Pull Requests

A Pull Request (PR) is a proposal to merge changes from one branch into another.

Typical workflow:

**Create Branch → Make Changes → Push → Open PR → Review → Discuss / Modify → Merge**

Pull Requests are useful for:

- Code review
- Collaboration
- Open-source contributions
- Feature development
- Bug fixes

---

### 🐛 Issues

GitHub Issues can be used to track:

- Bugs
- Features
- Improvements
- Tasks
- Questions

A useful issue can contain:

**Problem → Expected Behaviour → Actual Behaviour → Steps to Reproduce → Additional Information**

Issues can also be connected with Pull Requests and project-management workflows.

---

### 🤝 Collaboration

For a team project:

**Repository → Issues → Branch → Changes → Commit → Push → Pull Request → Review → Merge**

Good collaboration practices:

- Use meaningful branch names
- Write clear commit messages
- Keep Pull Requests focused
- Review code before merging
- Pull remote changes regularly
- Document important setup instructions
- Avoid committing secrets

---

### 🔐 Never Commit Secrets

Do not push sensitive information such as:

- API keys
- Passwords
- Access tokens
- Private credentials
- Database passwords
- `.env` files containing secrets

Use environment variables and appropriate secret-management methods instead.

A `.gitignore` file can prevent selected files from being tracked.

Common examples:

`.env`

`node_modules/`

`__pycache__/`

`*.log`

---

### 🏗️ GitHub Repository Structure

A professional repository may contain:

| File / Folder | Purpose |
|---|---|
| `README.md` | Explains the project |
| `LICENSE` | Defines how the project can be used |
| `.gitignore` | Specifies files Git should ignore |
| `src/` | Source code |
| `docs/` | Documentation |
| `tests/` | Tests |
| `CONTRIBUTING.md` | Contribution guidelines |

The exact structure depends on the project.

---

### 🧪 Practical Git Workflow

For a project you are actively developing:

**1. Pull the latest changes**

`git pull`

**2. Make your changes**

Edit your code.

**3. Check what changed**

`git status`

**4. Review the changes**

`git diff`

**5. Stage the changes**

`git add .`

**6. Commit**

`git commit -m "Describe the change"`

**7. Push**

`git push`

This creates a repeatable development cycle.

---

### ⚠️ Common Git Mistakes

- Committing without checking changes
- Using unclear commit messages
- Working directly on `main` for every feature
- Forgetting to pull remote changes
- Accidentally committing secrets
- Using force push without understanding its consequences
- Ignoring merge conflicts
- Uploading unnecessary generated files
- Treating Git and GitHub as the same thing

When a remote repository has newer commits, understand the changes before deciding how to integrate them.

## 🧭 How to Choose a Direction

You do not need to decide your entire Computer Science career at the beginning.

The goal is to explore different areas, understand what the work looks like, and gradually identify what interests you.

### 🔎 Start With What You Enjoy

Ask yourself:

| If you enjoy... | You may want to explore... |
|---|---|
| Building websites and applications | Software Engineering |
| Working with data and finding patterns | Data |
| Mathematics, models and intelligent systems | AI & Machine Learning |
| Servers, deployment and infrastructure | Cloud & Infrastructure |
| Finding vulnerabilities and protecting systems | Cybersecurity |
| Understanding how computers work internally | Systems & Core Computing |
| Product ideas, design, research or communication | Other Paths |

These are starting points, not fixed rules.

---

### 🧪 Explore Before Choosing

Instead of choosing a path only because it sounds interesting:

**Explore → Build → Reflect → Go Deeper**

Try small experiences from different areas:

- Build a simple web application
- Analyze a dataset
- Train a basic ML model
- Deploy an application
- Complete a beginner cybersecurity lab
- Write a C program and explore memory or processes
- Design a small product or research idea

You learn more about a field by doing than by only reading about it.
